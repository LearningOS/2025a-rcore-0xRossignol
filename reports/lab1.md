## **功能实现总结**

本次实验的核心是实现了一个名为 sys_trace 的新系统调用。该系统调用为任务提供了三个核心的自省功能：首先，它可以读取任务自身地址空间中任意位置的单个字节；其次，它可以向任意位置写入单个字节；最后，也是最重要的，它能够查询当前任务对任一系统调用的历史调用总次数。

为实现此功能，我们扩展了任务控制块（Task Control Block）的数据结构，为其增添了一个用于记录所有系统调用次数的数组。同时，我们修改了内核的系统调用分发入口，使其在处理任何系统调用之前，先对相应的计数器进行累加。sys_trace 的实现逻辑则根据传入的参数，分别执行内存读、内存写或查询计数值的操作，从而完整地实现了设计要求。

## **简答作业**

1 正确进入 U 态后，程序的特征还应有：使用 S 态特权指令，访问 S 态寄存器后会报错。 请同学们可以自行测试这些内容， 描述程序出错行为，同时注意注明你使用的 sbi 及其版本。

使用 **RustSBI 0.3.0-alpha.2**。在 U 态下运行三个 bad 测例，其出错行为和原因如下：

- **ch2b_bad_instructions.rs (执行 S 态特权指令)**
  - **代码行为**: 该程序在 main 函数中尝试直接执行 sret 指令。
  - **出错现象**: 程序执行后，内核会立即捕获到一个异常。终端会打印出内核的错误日志，内容类似：[kernel] Illegal instruction in application。日志会清晰地指出异常的原因（cause）是“非法指令”（Illegal Instruction, code 2），并报告发生异常时 PC 指针的位置（sepc）。随后，内核会终止这个出错的应用程序，并调度下一个程序运行。测试程序中的 panic! 语句永远不会被执行。
  - **原因分析**: sret 是一条 supervisor-level（S 态）的特权指令，其功能是从 S 态返回到低特权级（U 态）。当 CPU 已经处于 U 态时，它没有权限执行这条指令。因此，当 U 态程序尝试执行 sret 时，CPU 的保护机制会立即生效，触发一个“非法指令”异常，并将控制权强制交还给内核的 Trap 处理程序进行处理。
- **ch2b_bad_register.rs (访问 S 态 CSR 寄存器)**
  - **代码行为**: 该程序尝试使用 csrr 指令读取 S 态的控制状态寄存器 sstatus 的值。
  - **出错现象**: 其现象与上一个测例几乎完全相同。内核会捕获到“非法指令”异常，打印出 [kernel] Illegal instruction in application 的错误信息，并终止该应用。程序中用于打印 sstatus 值的 panic! 也不会被执行。
  - **原因分析**: RISC-V 架构对 CSR（控制状态寄存器）的访问权限有严格的规定。sstatus 是一个 S 态专属的 CSR，U 态程序只允许访问 U 态的 CSR（如 ustatus）。尝试在 U 态下读写一个 S 态 CSR，同样被处理器视为一次非法操作，会触发和执行特权指令一样的“非法指令”异常。
- **ch2b_bad_address.rs (访问非法内存地址)**
  - **代码行为**: 该程序尝试向地址 0x0 写入一个字节。在大多数内存布局中，零地址是无效的、未映射的，或者是受保护的区域，U 态程序无权访问。
  - **出错现象**: 内核会捕获到一个内存访问相关的异常。终端会打印出更具体的错误日志，例如：[kernel] PageFault in application。日志会指明异常原因是“存储/写入缺页”（Store/AMO page fault, code 15），并会通过 stval 寄存器的值报告导致错误的确切地址（即 0x0）。同样，该应用会被内核终止，其 panic! 不会被执行。
  - **原因分析**: 这体现了操作系统的内存保护机制。当 U 态程序试图访问一个虚拟地址时，CPU 的 MMU（内存管理单元）会进行地址翻译和权限检查。由于地址 0x0 对于该用户程序来说是无效或不可写的，MMU 会阻止这次内存写入操作，并触发一个缺页异常（Page Fault），将控制权交给内核。内核的 Trap 处理程序识别到这是一个非法的内存访问后，会采取措施（通常是终止进程）来保护系统的稳定性。

2 深入理解 trap.S 中两个函数 `__alltraps` 和 `__restore` 的作用，并回答如下问题:

1. L40：刚进入 __restore 时，sp 代表了什么值。请指出 __restore 的两种使用情景。

- **sp 的值**: 此时，sp (栈指针) 指向当前任务**内核栈**上的特定位置，即 trap_handler 函数返回后，TrapContext 结构体的**起始地址**。__restore 的工作就是从这个地址开始，将 TrapContext 中保存的所有寄存器值恢复到 CPU 的物理寄存器中。
- **两种使用情景**:
  1. **从 Trap 返回**: 当一个系统调用、异常或中断在内核态处理完毕后，trap_handler 函数会返回，接着执行 __restore。此情景的目的是恢复被中断的用户程序上下文，让它从中断点无缝地继续执行。
  2. **任务首次启动**: 当一个任务第一次被调度运行时，内核会为其在内核栈上“伪造”一个 TrapContext，并将 sepc 设置为用户程序的入口地址。然后，调度器会直接跳转到 __restore。__restore 会“恢复”这个伪造的上下文，其效果就是将 CPU 的状态设置为用户程序的初始状态，并跳转到程序的第一条指令开始执行。

2. L43-L48：这几行汇编代码特殊处理了哪些寄存器？这些寄存器的的值对于进入用户态有何意义？请分别解释。

- 这几行代码特殊处理了 **sstatus**、**sepc** 和 **sscratch** 这三个 S 态的 CSR。
- **csrw sstatus, t0**: 恢复 sstatus (Supervisor Status Register) 寄存器。它的意义在于**设定返回后的 CPU 状态**：
  - 通过恢复 sstatus 中的 SPP (Supervisor Previous Privilege) 位为 0 (U-mode)，它明确告诉 sret 指令执行后需要将特权级**切换到 U 态**。
  - 通过恢复 SPIE (Supervisor Previous Interrupt Enable) 位，它决定了返回 U 态后 CPU 是否要重新响应中断。
- **csrw sepc, t1**: 恢复 sepc (Supervisor Exception Program Counter) 寄存器。它保存了用户程序应当**从哪里继续执行的指令地址**。sret 指令会读取 sepc 的值并将其加载到 PC（程序计数器）中，从而实现精确的上下文恢复。
- **csrw sscratch, t2**: 恢复 sscratch (Supervisor Scratch Register) 寄存器。在这里，它将 TrapContext 中保存的**用户栈指针**加载到 sscratch 中。这一步是为了给后续的 csrrw sp, sscratch, sp 指令做准备，以便能够正确地换回用户栈。

3. L50-L56：为何跳过了 x2 和 x4？

- **x2 (sp)**: x2 是栈指针。在恢复其他所有通用寄存器的过程中，我们正依赖 sp 作为基址指针来从 TrapContext 中加载数据（例如 ld x1, 1*8(sp)）。如果此时就恢复 sp 的值，它会立即指向用户栈，我们就丢失了对内核栈上 TrapContext 的访问能力，导致后续的寄存器恢复失败。因此，sp 必须在最后通过一个特殊的原子交换指令来恢复。
- **x4 (tp)**: x4 是线程指针。根据代码中的注释 "application does not use it"，在这个阶段的 rCore 实现中，tp 寄存器没有被用作需要在用户态和内核态之间传递状态的上下文信息。因此，为了效率，省略了对它的保存和恢复。

4. L60：该指令 csrrw sp, sscratch, sp 之后，sp 和 sscratch 中的值分别有什么意义？

- 这是 __restore 中返回用户态前的最后一次栈交换。
- **sp 的意义**: sp 的值变成了**用户栈的指针**。这个值是从 sscratch 中读取的（我们在 L48 已将其存入 sscratch）。此时，CPU 的栈指针已经正确地指向了该任务的用户空间栈，为返回用户态后的函数调用和局部变量分配做好了准备。
- **sscratch 的意义**: sscratch 的值变成了当前任务的**内核栈指针**。这个值是交换前 sp 的值。这个操作将内核栈的地址“停放”在 sscratch 中，以备下一次发生 Trap 时，__alltraps 可以通过相同的交换指令立即切换回内核栈。

5. __restore：中发生状态切换在哪一条指令？为何该指令执行之后会进入用户态？

- 发生状态切换的指令是 **sret**。
- sret 是一条 S 态特权指令，其设计目的就是从 supervisor 模式返回。它执行时会原子地完成几项关键操作：
  1. **切换特权级**: sret 会检查 sstatus 寄存器中的 SPP 位。因为我们之前已经恢复了 sstatus 并将 SPP 设置为指向 U 态，sret 会将 CPU 的特权级从 **S 态切换到 U 态**。
  2. **跳转到返回地址**: 它将 sepc 寄存器中的值加载到 PC（程序计数器）中，使程序从被中断的地方继续执行。

6. L13：该指令 csrrw sp, sscratch, sp 之后，sp 和 sscratch 中的值分别有什么意义？

- 这是 __alltraps 的第一条指令，是进入内核时的栈切换。
- **sp 的意义**: sp 的值变成了当前任务的**内核栈指针**。这个值是在上一次 __restore 过程中被保存在 sscratch 里的。执行该指令后，CPU 的栈操作立即切换到了安全的内核栈上，防止用户栈的溢出或恶意数据破坏内核。
- **sscratch 的意义**: sscratch 的值变成了刚刚发生 Trap 时的**用户栈指针**。这个值是交换前 sp 的值。它被临时保存在 sscratch 中，稍后（在 L31）会被读取并保存到内核栈的 TrapContext 结构体中。

7. 从 U 态进入 S 态是哪一条指令发生的？

- 对于系统调用，这条指令是 **ecall** 。
- 当 U 态程序执行 ecall 指令时，它会触发一个同步异常。这会导致 CPU 硬件自动地、原子地完成从 U 态到 S 态的切换，同时保存返回地址（到 sepc）和异常原因（到 scause），然后跳转到 stvec 寄存器指定的 Trap 处理入口（即 __alltraps）开始执行内核代码。对于中断或缺页等其他异常，虽然不是由一条特定指令触发，但硬件完成的 U->S 状态切换过程是类似的。
