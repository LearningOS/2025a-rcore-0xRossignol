## 功能实现总结

本次实验在内核中实现了死锁检测机制。通过在 `mutex_lock` 与 `semaphore_down` 系统调用中引入资源依赖分析，利用银行家算法判断系统是否处于安全状态，从而防止线程间循环等待导致的死锁。实现了 `sys_enable_deadlock_detect` 系统调用，使得进程可按需启用或关闭死锁检测功能。当检测到潜在死锁时，系统拒绝资源申请并返回错误码 `-0xDEAD`。实验中对等待图、资源分配表等结构进行了设计与维护，并验证了在多线程场景下死锁检测的正确性与性能。

## 问答作业

### 一

> 在我们的多线程实现中，当主线程 (即 0 号线程) 退出时，视为整个进程退出， 此时需要结束该进程管理的所有线程并回收其资源。 
>
> - 需要回收的资源有哪些？ 
> -  其他线程的 TaskControlBlock 可能在哪些位置被引用，分别是否需要回收，为什么？

需回收：

- **用户态资源**：如页表、文件描述符表、用户栈、内核栈；
- **内核态资源**：包括所有线程的 `TaskControlBlock`、分配的内核栈页帧、等待队列中的引用；
- **同步原语资源**：如 `Mutex`、`Semaphore` 等锁对象的占用与等待记录；
- **地址空间资源**：进程的 `MemorySet`（页表映射）与物理页帧。

#### 其他线程的 `TaskControlBlock` 可能在哪些位置被引用？是否需要回收？

- **调度队列 (ready_queue)**：其他线程可能尚未运行完，应将其从调度队列中移除并回收；
- **等待队列 (wait_queue)**：线程可能阻塞在某个锁或信号量上，需清理等待队列中的引用；
- **父子进程或内核全局表**：线程退出后，其 TCB 不再被引用，应释放。

### 二

> 对比以下两种 `Mutex` 中的实现，二者有什么区别？这些区别可能会导致什么问题？

|              | Mutex1                                       | Mutex2                                                       |
| ------------ | -------------------------------------------- | ------------------------------------------------------------ |
| **加锁逻辑** | 使用循环反复尝试锁定，只有在锁释放后立即重试 | 仅尝试一次，若失败则直接阻塞                                 |
| **解锁逻辑** | 释放锁并唤醒一个等待任务                     | 唤醒任务时不立即释放锁，需等待下次唤醒任务解锁               |
| **公平性**   | 较高，线程按 FIFO 等待                       | 较低，可能导致饥饿或重复阻塞                                 |
| **可能问题** | 开销略大（忙等+上下文切换）                  | 若多个线程同时唤醒，可能导致锁状态错误（未原子切换）或锁长期被占用 |
